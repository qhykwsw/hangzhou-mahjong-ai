# 由迭代 Agent 推进的规则线与 RL 线

2026-09-24 决定，2026-09-25、2026-09-27 修订：迭代改由受限的迭代 Agent 推进，任何会话、任何模型都能接续。

自动研究的规则分支经过几百轮迭代后收益已经很小，最近还出现了倒退。18 个历史冠军的大乱斗显示，结构最简单、专注于「速度优先、必胜时追求翻倍」的版本最强，而层层叠加修正的分支掉到了中游。所有分支都继承同一个初始策略，研究 Agent 受它影响很大，很多观察和动作空间从来没有尝试过，只在细节上反复微调。

## 决定

- 新建人工项目 `projects/personal/firstprinciples/`，推进两条迭代线：规则线从最朴素的牌效策略起步、按杭州麻将规则的第一性原理逐步扩展；RL 线沿用训练方案框架，逐次修改训练方案。迭代方式参照 autoresearch：每次从当前最好版本出发只改一处、固定预算评估、每次尝试都记录、只继承确认成功的尝试、不设终点。
- 评估不走研究框架。每次尝试面对同一个固定对手池（7 个强且风格各异的版本：最初是 6 个研究规则加一个模仿模型，2026-09-28 起是 7 个规则，见下文「更换固定对手池」），每场被评估版本坐一个座位，其余三座从对手池取三个，阵容与座位按固定顺序轮换。得分是它对对手池的场均桌面分，两条线的得分可直接比较。规则线在 Mac 本机评估，RL 线在训练它的 GPU 主机上就地评估。模型座位在所有设备上以 fp16 推理，不同显卡之间极少数近似平局的取整可能不同，配对比较不受影响，因为两边面对同一批座位。
- 为避免反复在同一批牌局上挑选造成高估，评估分开发集与确认集：每个版本都打满固定的 16384 场开发牌局，一个版本只有一个成绩（2026-09-25 取消了 4096 → 8192 → 16384 场的阶梯与提前淘汰）；开发集得分超过当前最好成绩后，再在全新牌墙上与最好版本各打 8192 场做配对确认，单侧 90% 下界大于 0 才算成功。
- 评估时限收紧到出牌 2.0 秒、应答 0.6 秒，超时按平台默认动作代打，策略算力不另设上限，超时代价直接体现在得分里。
- **规则线的计算效率与等价替换（2026-09-27）。** 规则版本的每决策耗时决定三件事：规则线自己开发集评估的时长、RL 线蒸馏时教师标注的时长（教师每决策 8 ms 时，标注约占 RL 每次训练的六成）、比赛多桌并发时的超时风险。耗时主要花在规则策略自己的枚举与递归上，不在共享 SDK，所以提速由规则线自己做：每个规则结果都报告每决策耗时及此前最好版本的对照，实现效率是它的设计约束。只提速不改决策的版本在开发集上与最好版本配对差为 0，过不了「超过最好成绩」这一关，因此走等价替换：不跑开发集，在数千局新牌局里让新代码与最好版本面对同一批局面、逐个决策比较，全部一致就沿用最好版本的成绩成为新的最好版本，有一处不同即判不等价。固定对手池里的慢规则成员同样可以由维护者登记等价实现：对手池身份与已有成绩不变，评估与训练执行时换用快版，登记前的逐决策比较用更多牌局，因为它此后出现在每一场评估与训练里。
- **更换固定对手池（2026-09-27）。** 固定对手池可以整体更换，用来让对手的风格更全、更强；换池就开始新的评估口径。为了不让迭代线从头开始，换池时先排空（不开新尝试，在途尝试跑完），再把两条线每个成为过最好版本的版本和自由对战上场版本在新池下重打开发集，沿用原编号记入新池；每条线取重算分最高的版本作为它在新池下的最好版本。从十来个版本里取最高分会略微偏高，之后的尝试仍要过确认集，这点偏差由后续确认吸收。2026-09-28 的第二代对手池是 7 个规则，全部由规则线 fp-rule-033 的估值框架改出不同的打法：保留竞速估值的经典版、去掉白板升级的平打、吃与碰只看速度的两个版本、见杠就杠、向听数远时门清、耐心等大牌；每个成员在旧池开发集上都超过旧池最强成员，都建在 033 的快速实现上；成员的缓存限制在几千条，因为对局进程里七个成员共用一个解释器，大缓存会让全量垃圾回收停顿一秒以上，停顿落在谁的决策上谁就超时，各主机的超时多少又不同，分数就随主机变化。研究候选里没有比旧池更强的，所以用自己的代码；代价是规则线此后的对手与自己同源，可能偏向打赢这一家族的打法，成员之间因此只保留决策规则明显不同的版本，并且不放两条线的原版。模型成员退出：RL 线当时的模型九成八的决策与教师相同，加进池里只增加推理成本、不增加风格；RL 线稳定超过规则后再考虑放回。
- 评估只为速度而设计，不为研究 Agent 的隔离付代价：对手池的代码包在对局进程内运行，每个进程同时打几桌，模型座位共用主机的推理服务；这些执行方式不改变对局结果，也不进对手池 id。运行时从 `src/mahjong_ai` 冻结，换运行时要重建对手池并重跑参照。
- **角色分开。** 迭代 Agent 只改本线的策略目录：规则线的 `rule/`，RL 线 `rl/recipe/` 里的训练内容。评估代码、对手池、训练框架、训练预算、按主机的执行参数与资源上限归维护者（用户或其授权的会话）。维护者把这些条件一并封存；任何一项变了，harness 就拒绝开始或续跑尝试，直到维护者重新封存。缩短的场数与预算只在单独的流程检查记录（`FP_LOCAL`）里被接受。迭代 Agent 认为必须改基础设施时，停下来交给用户。
- **与会话解耦。** 用户在 Claude Code 或 Codex 里说「开始/继续执行规则迭代」或「开始/继续执行 RL 迭代」，那个会话就成为迭代 Agent；「开始」与「继续」是同一件事。尝试在脱离会话的驱动进程里运行，全部状态写在磁盘上，驱动进程死后由下一次等待命令重新拉起并从原阶段续跑；Agent 在同一回合里反复调用最多 9 分钟返回一次的等待命令，不依赖 `/loop` 之类某个客户端独有的唤醒机制。尝试记录带着每次的假设与基础版本，各线另有迭代 Agent 维护的迭代笔记，换会话、换模型都能接上。同一条线同一时间只有一个会话持有推进权，等待命令顺带续约，20 分钟未续约即失效，用户说「接管」可强制转移。
- **每次设计前恢复最好版本。** 等待命令在返回「设计」之前把本线目录恢复成当前最好版本，最好版本有变化时只提交这个目录；开跑时拒绝不是从当前最好版本恢复来的目录。这样并行尝试的改动不会叠加，崩溃会话留下的半成品也不会混进下一次尝试，迭代 Agent 不需要碰 git。
- **RL 线的预算与约束。** 用最小的模型（128/4/4），不设时间上限。每次尝试的训练局数由迭代 Agent 选，默认 100 万、最多 500 万（2026-09-27 起，此前固定 100 万）：策略梯度每步要 7 万～23 万局才越过噪声，100 万局里的 RL 段只够走几个低于噪声的小步；500 万局纯 RL 约占一台主机半天以内，三个尝试位每天仍能出十个以上结果。尝试也可以从设计时的最好版本接着训练，而不是从起点重来：训练量沿迭代线累积，每一段仍要在开发集和确认集上超过最好版本才被继承，所以累计量不另设上限。起点是同一模型对 piao-call-channel 模仿 10 万局（每场 16 局）。采集的进程数、桌数与攒批由 harness 按主机固定，因为它们也决定训练牌局与桌面负载；训练时框架随时检查进程组的进程数、显存占用、内存与 torch 线程数，超出即结束训练。训练对手与教师由方案自选：默认是固定对手池与 piao-call-channel，可换成清单里的固定对手池成员或两条线每一个成为过最好版本的版本（规则才能当教师）；评估对手池始终不变。方案只能通过框架的采集接口打训练局，开跑前静态检查导入；训练局数超出预算 2.5 万局以上的尝试记为无效。规则策略同样不开进程和线程池，否则会在对局里抢走同桌对手的 CPU。
- **RL 线的主机。** 4070、4090 与 5070 Ti 是三个尝试位，共享一个最好版本。三台的资源上限各自按主机设定，不求统一；迭代 Agent 从在线且空闲的主机里选一台，按它的资源设计新尝试，随资源变化的量在方案里从运行时读取。最初的最好版本就是模仿起点本身，由维护者在完整开发集上评一遍，所以三台主机从一开始就能各朝一个方向分叉，和之后的任何分叉一样；规则线只有一个评估位，第一次尝试是 v0 原样。主机离线时在途尝试等它回来；主机重启丢了训练时，尝试用同一份快照排队，由任一空闲主机重做，并排在新设计之前；这些都不算尝试的结果。用户可以随时关闭或开启某台主机，默认让在跑的尝试跑完，明确要求时立即撤下并排队重做；主机只借用到某个时间时预约关闭，到点即撤下排队重做，此前迭代 Agent 在设计时看得到剩余时间。
- **自由对战。** 新的最好版本在开发集上与自由对战的上场版本配对，下界大于 0 时标出「高于参照线，可以上场」，迭代 Agent 把问题转给用户并照常迭代；用户同意后由 harness 导出迭代线版本并改写上场版本。
- 研究实验保持暂停，状态与历史不动。

## 考虑过的替代方案

- 在研究框架里新开分支：框架的评估对手、晋级与大乱斗节奏为多个 Agent 分支并行设计，套用本方案等于改框架协议。
- 每次尝试都换新牌墙并重打最好版本：不存在选择偏差，但每次尝试的成本翻倍；开发集加确认集只在少数成功尝试上付这笔成本。
- 开发集按 4096 → 8192 → 16384 场分段、明显落后即停（本决定的初版）：能省下明显变差的尝试约四分之三的评估时间，但同一个版本会因为场数不同出现几个成绩，参照也只打到第一段，与需要全段配对的尝试对不齐。
- 与各对手逐一单挑：可以测出正面交锋的强弱，但与平台比赛「一人面对三家」的形态不一致。
- 维护者（Claude 本人）用 `/loop` 亲自推进（本决定的初版）：只有 Claude Code 能跑，在途尝试挂在会话的后台进程上，会话一断就成了孤儿；迭代 Agent 还能顺手改评估与框架，条件漂移无从察觉。
- RL 的三台主机各为一条独立子线：进展分散到三处，还要另设合并规则；共享一个最好版本时，任何主机上的成功都立刻被后续尝试继承。
- 主机离线一段时间后就把尝试换到别的主机重跑：结果来得更快，但只是断网时远端任务其实还在，重跑会白白占用另一台主机一个多小时，还要清理原主机上的残留任务。
- RL 单次局数不设上限或定为 1000 万：一次尝试要占主机一天左右，探索期出结果太慢；想要更大的训练量，用从最好版本续训的方式累积。
- 累计训练量也设上限：续训只在确实变强时被继承，上限只会截断仍在进步的路径。
- 由维护者或 RL 线把慢的规则版本转写成快版本：冻结版本不应再改，规则线每出一个新的最好版本就要重做一次，转写者也不熟悉估值的来龙去脉，容易改出偏差。
- 等价检查容许少量决策不同，再用开发集判非劣：纯提速本来就不该改变决策，放宽就要另设非劣效门槛和额外评估时间；先要求逐位一致，浮点运算顺序在实践中卡住太多提速时再议。
- 仅在手册里约定迭代 Agent 不改评估条件：不同模型、不同会话对约定的遵守程度不同，封存让任何改动都当场可见。
