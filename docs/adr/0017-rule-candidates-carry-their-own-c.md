# 规则线候选自带 C 代码

2026-09-28 决定：规则线的候选可以带自己的 C 代码（`native.c`），估值等热路径从第一次提交起就写成 C，而不是先写 Python、成为最好版本后再做等价替换提速。

对手池成员移植到 C 之后，规则线在 Mac 上的评估有八成时间花在被评估的候选自己身上。候选只能写 Python，而运行时里的 C 原语只提供现成的计算，所以每个改动估值的新想法都先以 Python 速度评估，要提速还得等维护者把新逻辑补进运行时，再由规则线做一次等价替换，这是事后补救。fp-rule-046 的估值移植到 C 后，单个决策快 5.5～10 倍，而评估时长正是规则线迭代速度最大的约束。

## 决定

- 规则包里可以放 `native.c` 及其旁边的 `.h`，和 `strategy.py` 一起冻结。策略用 `native = _fast.load_native(__file__)` 取得它编译出的扩展模块（模块名 `native`）。`load_native` 在运行时的 `_fast` 里：按源码、同目录头文件、运行时的 `_fast.c`、Python ABI 与编译参数计算哈希，在每台机器上只编译一次，缓存在包外（`~/.cache/leihuo_majiang/native`，可用 `MAHJONG_NATIVE_CACHE` 改），所以包的哈希不变；同一进程里各包的模块互不干扰。
- C 代码可以 `#include "_fast.c"`，直接调用运行时的全部 C 原语（向听、进张分析、面子表、竞速估值等）。编译参数固定为 `-O3 -ffp-contract=off`：浮点按书写顺序舍入，照 Python 的运算顺序写就能逐位一致。
- 开跑前 harness 在对手池运行时下预编译：编译不过就不开跑，并返回编译器报错；预编译同时填好本机缓存，评估时不会因为现场编译而超时。GPU 主机上用到规则版本（例如作为教师）时，在首次加载时编译。
- 与 Python 代码受同样的约束：C 源码不得开进程或线程、不得加载其他代码、不得回头调用 Python 解释器执行或导入代码，开跑前的源码检查会拦下这些用法。
- 编码走 `_fast` 里的新函数，对运行时只是新增：对手池可以原池升级，身份和成绩都不变。

## 考虑过的替代方案

- **维持现状**：新想法先用 Python 验证，成为最好版本后再由维护者补 C、规则线做等价替换。每个改估值的尝试都要以 Python 速度评估一次，维护者成为瓶颈。
- **把更多计算参数化进运行时**：规则线只能在维护者预设的参数空间里改动，限制了第一性原理的探索。
- **让候选用 ctypes/cffi 自己加载**：这等于放开源码检查禁止的导入，编译与缓存也会分散到各个候选里。

## 后果

- 规则线的每个想法都要写 C：开发变慢，也更容易出崩溃类的错误。崩溃在评估里记为报错，不会混进成绩。
- 需要 C 编译器和 setuptools。Mac 与各 GPU 主机本来就要编译 `_fast`，已经具备。
- 候选的 C 若 include 了 `_fast.c`，就按编译时运行时里的版本锁定：原池升级改了竞速部分后，旧候选重新加载时会按新的 `_fast.c` 重新编译。升级时维护者会重放规则线最好版本，更早的版本属于历史记录，不再重放。
