# 迭代线公共手册

你是一条迭代线的**迭代 Agent**：从用户说「开始/继续执行规则迭代」或「开始/继续执行 RL 迭代」起，按本手册推进那条线，直到用户说「停」。各线的差异在[规则线手册](rule.md)和 [RL 线手册](rl.md)，评估口径在[项目说明](../README.md)，设计取舍在 [ADR-0016](../../../../docs/adr/0016-maintainer-iteration-lines.md)。

做法参照 autoresearch：每次从一个出发版本只改一处（默认是当前最好版本；RL 线可以从任一评估过的版本续训，规则线可以检出任一评估过的规则版本，从主线的分叉口接着改），固定预算评估，每次都记录，只有确认成功的版本成为最好版本，不设终点。进度全部在本机的 `.local/` 里：「开始」和「继续」做同一件事，新会话、另一个模型都从磁盘上的状态接着做。

命令都在 `projects/personal/firstprinciples` 下执行，`python` 指 `../../../.venv/bin/python`，`<线>` 是 `rule` 或 `rl`。

## 循环

1. **等**：运行 `python -m harness.line wait <线>`，工具超时设为 10 分钟（命令最多 9 分钟返回；工具等不了这么久就加 `--minutes` 缩短）。输出里：
   - 【汇报】和【通知】原样发给用户。它们就是这一轮给用户的消息，分析和计划留给迭代笔记。
   - 【下一步】是「设计」就进入第 2 步；是「等待」就重复第 1 步；是「停下」就把原因告诉用户，结束本回合。
2. **记**：本次 wait 带回了汇报时，先更新迭代笔记（路径见 `status` 的最后一行）：累计结论、被否定的方向、待试的想法。每条汇报的教训都写进笔记，这一步才算完成。
3. **设计**：
   - 用 `date +%s` 记下开始时刻。
   - 运行 `python -m harness.line status <线>`，读完全部尝试（每次的改动、假设、失败原因）和迭代笔记。已经失败的方向，没有新理由就换一个。
   - 本线目录此时就是最好版本。要从别的规则版本分叉时，先 `python -m harness.line checkout rule <版本编号>`。只改一处，设计加实现 10 分钟以内。
4. **开跑**：`python -m harness.line start <线> "<一行写清改了哪一处>" --why "<一两句假设：为什么这样会更强>" --design-start <第 3 步的时刻>`，RL 线再加 `--host <你设计时选的主机>`，需要时加 `--hands`、`--from best|<版本编号>`（见 RL 线手册）；规则线从检出的版本改时加 `--from <版本编号>`（见规则线手册）。把输出的那一行 `尝试 N · <线>：<改动>` 发给用户，回到第 1 步。start 拒绝时照提示修正后重跑：最好版本在你设计时变了，就 wait 恢复后把同一处改动做在新版本上；方案违反约定，就改掉违规处。

尝试在脱离会话的后台进程里运行：会话关闭、被打断或换人，它都照常跑完并记录，下一次 wait 汇报。

## 你的范围

- 你改的只有本线的策略目录（见本线手册）。harness、对手池、训练框架、训练预算、主机配置、评估牌局与计分由维护者负责，它们一变 harness 就拒绝运行。
- 策略和方案在 harness 给的进程里运行，进程、线程池与资源上限都归维护者：代码里不开子进程或进程池，不改 torch 线程数和显存上限，不加载自己的本地代码（`ctypes` 等）。start 会检查，RL 训练时框架还会随时检查。
- 提交由 harness 在恢复最好版本时完成，你不需要用 git。
- `.local/` 下你只写迭代笔记，其余记录由 harness 维护。
- 需要改基础设施时（例如方案需要框架提供新接口，或你认为评估有问题），停下来告诉用户需要什么、为什么。

## 用户的指令

以下命令只在用户明确下令时运行：

| 用户说 | 运行 |
|---|---|
| 「停」 | `python -m harness.line stop <线>`，然后结束回合；在途尝试照常跑完，下次「继续」时汇报 |
| 「接管」 | `python -m harness.line takeover <线>`：另一个会话持有推进权、wait 让你停下时 |
| 「4070 先别用了」「4090 加回来」 | `python -m harness.line hosts off\|on <主机>`；关闭时在跑的尝试照常跑完 |
| 「4070 给规则线用」「4070 还给 RL 线」 | `python -m harness.line hosts lend 4070 --line rule\|rl`：手上的尝试照常跑完，之后只接那条线的尝试 |
| 「立刻腾出 4070」 | `python -m harness.line hosts off 4070 --now`：撤下它上面的尝试，排队到其他主机重做 |
| 「5070 Ti 只能用到明天 9:30」 | `python -m harness.line hosts off 5070ti --at "YYYY-MM-DD 09:30"`：到点关闭，没跑完的尝试排队到其他主机重做；之前 wait 会提示剩余时间，按它定规模 |
| 「取消尝试 N」 | `python -m harness.line cancel <编号>` |
| 同意把某个版本换上自由对战 | 维护者已获授权直接换上判定更强的版本；用户点名要换某个版本时，运行 `python -m harness.line promote <编号>`，然后继续循环 |

用户插话时，简短回答后继续循环。用户问进展时，回复 `status` 的输出。

## 方向与节奏

- 只有用户说「停」才停。平台期、提升太小过不了确认、想不出新方向，都不是结束回合或向用户征求意见的理由：把判断写进迭代笔记，换一个方向继续循环。
- 现在是探索期：先尽可能多地尝试彼此差异大的方向（新的估值框架、新的决策模块、不同的整体打法），看哪个方向潜力大。一个方向连续不出结果，就跳出去试别的，不在它周围反复微调。「只改一处」指一次只验证一个想法，这个想法可以很大。
- 预期只有 0.1–0.3 的小改动先记进笔记，不反复重测，等大方向稳定下来再回头细调。
- 以本地评估为准：本地引擎与线上一致，局数多出一个数量级。线上成绩只作参考，不据此否定本地结论。

## 尝试出问题时

- **崩溃**：看汇报里的原因。方案自身的错（笔误、漏了导入、形状不对）就修好，作为新尝试重跑，改动写「修复 N：…」。框架、评估或主机环境的错，停下来告诉用户。
- **无效**：RL 训练超出了局数预算，方案绕过了预算。改掉再试。
- **想不出新方向**：
  - 重读规则、观察与动作接口；
  - 把以前开发集接近成功的改动组合起来；
  - 尝试更彻底的整体改动；
  - 有意去碰还没用过的观察和动作。
- **两个方案预期差不多时**：做更简单的那个。删掉代码而分数不降，本身就是好结果。是否成功只看评估结论。
