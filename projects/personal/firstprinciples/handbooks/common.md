# 迭代线公共手册

规则线和 RL 线各由一个独立的 Claude Code 会话推进，两个会话都遵守本手册，各自的差异写在[规则线手册](rule.md)和 [RL 线手册](rl.md)。评估口径见[项目说明](../README.md)，设计取舍见 [ADR-0016](../../../../docs/adr/0016-maintainer-iteration-lines.md)。做法参照 autoresearch：一次只改一处，固定预算评估，每次都记录，只继承成功的版本，不设终点。

用户用 `/loop` 启动会话，每次唤醒完成一轮。规则线每轮至多一次尝试；RL 线管三台 GPU 主机，每台主机至多一个在途尝试，哪台空了就在哪台开新尝试。下面的命令都在 `projects/personal/firstprinciples` 目录下执行，`python` 指 `../../../.venv/bin/python`。

## 每轮步骤

1. **起步检查**：本线手册的「起步」没完成就先做，这一轮只做起步，不开始尝试。
2. **等待**：本线（RL 线按主机）上一次尝试还在后台跑，就不开新尝试。它结束时会唤醒会话，另外安排一次 20～30 分钟的兜底唤醒，不要反复轮询。
3. **读历史**：运行 `python -m harness.evaluate history <线>`，查看全部尝试、当前最好版本、参照线和在途尝试（标着主机与已用时间）。已经失败的方向，除非有新的理由，不再重复。
4. **设计**：先用 `date +%s` 记下开始时刻。只改本线的一处，设计加实现不超过 10 分钟。
5. **开跑**：在后台运行本线的尝试命令（见本线手册），`--design-start` 传第 4 步记下的时刻，描述用一行写清改了哪一处。尝试编号由命令预留，开跑时只发一行：`尝试 N · <线>：<改动>`。
6. **汇报**：尝试结束后，把命令输出的汇报块原样发给用户，这是这一轮唯一的消息。汇报块包括尝试编号、结论、改动、得分与配对差、确认集结果、超时与报错、两条线的排名。不加分析，不写下一步，不写未探索的方向。
7. **收尾**：
   - 结论是「成功」：按路径提交本线的源码目录，提交信息写尝试编号和改动。
   - 其他结论：运行 `python -m harness.evaluate restore <线>`，把本线的源码目录恢复成当前最好版本。
   - RL 线各台主机的尝试各自与结束时的最好版本配对，先成功的先成为最好版本；其他主机的尝试若也成功，评估会自动改与新的最好版本确认。
   - 然后进入下一轮。

## 不能做

- 改 `harness/evaluate.py`、`.local/pool.json` 或 `.local/attempts.jsonl` 里的记录。评估代码一改，评估就会拒绝运行。只有用户明确同意，才可以运行 `python -m harness.evaluate seal` 重新冻结。
- 为了某次尝试改变评估条件：对手池、牌局、局数、时限、计分都不能动。
- 改另一条线的目录；用 `git add -A`、`git reset` 或 `git checkout` 波及本线目录以外的文件。
- 自己停下，或者问用户要不要继续。

## 与用户交互

- 用户插话：先简短回答，然后接着循环。
- 用户问进展：回复 `history` 的输出。
- 用户说「停」才停。停之前，如果还有正在跑的尝试，先告诉用户，由用户决定是等它跑完还是直接终止。

## 尝试出问题时

- **崩溃或报错**：如果是笔误、漏了导入这类小问题，修好后作为新一次尝试重跑，描述注明「修复 <编号>」。如果是思路本身行不通，保留这次记录，换一个方向。
- **想不出新方向**：
  - 重读规则、观察与动作接口；
  - 把以前开发集接近成功的改动组合起来；
  - 尝试更彻底的整体改动；
  - 有意去碰还没用过的观察和动作。
- **两个方案预期差不多时**：优先做更简单的那个。删掉代码而分数不降，本身就是好结果。是否成功仍然只看评估结论。
