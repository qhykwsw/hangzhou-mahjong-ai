# 规则线手册

先读[公共手册](common.md)。本手册只写规则线的差异，杭州麻将规则与计分见[平台规则](../../../../docs/reference/platform.md)。

| 项目 | 内容 |
|---|---|
| 你改的目录 | `rule/`（主要是 `rule/strategy.py`）。v0 是最朴素的牌效策略，只看向听和进张 |
| 目标 | 从规则的第一性原理出发，覆盖全部观察和动作空间，做出尽可能强的规则策略。大方向是速度优先、必胜时追求翻倍，整体上不防守。自动研究的分支都从同一个初始策略演化而来，视野偏窄；这条线要有意尝试它们没用过的观察和动作。对手池成员的源码可以参考，但不照搬 |
| 时限 | 策略的算力不设上限，但正式比赛是多桌并发，出牌 2.0 秒、应答 0.6 秒不能超。超时由平台默认动作代打，代价直接算进分数 |
| 主机 | Mac 本机评估，同一时间一个尝试。对手池全是规则，一轮开发集只要几分钟，确认集另算；每条记录的用时见 `status`。你在评估空闲时跑的本地实验会和评估抢 CPU，评估期间少开进程 |
| 快照 | start 把 `rule/` 冻结到 `.local/attempts/<编号>/package`，评估只用这份快照；wait 在设计前用最好版本的快照覆盖 `rule/`；要从别的版本分叉时用 `checkout`（见「从分叉点走没走过的路」） |

第一次尝试就是 v0 原样。它没有可比的版本，打完开发集后直接成为规则线的最好版本。

## 从分叉点走没走过的路

另起一套整体框架（路径 B，fp-rule-069～075）没有看到势头，已经停下（2026-09-30 用户决定）。规则线回到主框架：竞速估值这条从 v0 到当前最好版本的主线。出发点不必是最好版本。主线一路走来，很多分叉口当时想过另一条路却没走，现在可以回到那个版本，沿那条没走的路一步步做下去。

- 找分叉口：翻迭代笔记和记录里的假设（`--why`）、丢弃版本、「下一步也可以……」这类没做的想法，挑出当时有理由、却因为只能改一处或时间不够而放下的方向。
- 做法：wait 会先把 `rule/` 恢复成最好版本，你再运行 `python -m harness.line checkout rule <版本编号>` 检出分叉口的版本，改一处后运行 `start ... --from <版本编号>`。任何评估过的规则版本都能检出，成功与否都行。
- 进展看这条分支自己的开发集成绩：每个版本都打同一个开发集，`python -m harness.evaluate compare <A> <B>` 可以对当前对手池下任意两个版本逐组配对。分叉口版本在当前对手池下没有成绩时，拿这条分支的第一个版本作起点比。一条分支连续几步没有上升的势头，就换一个分叉口。
- 成为最好版本的标准不变：仍要在开发集和确认集上超过当时的最好版本。
- 迭代笔记里给每条分支单独记：分叉口版本、当时没走这条路的原因、每一步的开发集成绩、判断还有没有势头的依据。

## 计算效率

每决策耗时是规则线的设计约束，和分数一起看：

- 你的评估：开发集的时间主要花在你的策略上，每决策越慢，一天能做的尝试越少。
- RL 线：它从规则线的最好版本里选教师，蒸馏时学生遇到的每个决策都要教师算一遍，教师的每决策耗时直接决定 RL 每次训练的时长。
- 比赛：多桌并发时，最慢的那类局面决定会不会超时。

设计新模块时同时设计它的算法：先估算调用次数（每个决策 × 候选动作 × 摸牌种类 × 递归层数），在枚举之前剪掉不可能的分支，缓存纯函数，内层循环里少复制、少排序；SDK 已有的函数（C 实现）直接用。每个规则结果都报告每决策耗时和此前最好版本的对照，`status` 里每条记录也有；一个模块让耗时成倍上升，先把它的实现做快再开跑。

缓存要小。评估的对局进程里坐着你的版本和对手池的规则，每次全量垃圾回收都要走遍每个缓存的每一条：缓存到几十万条时一次回收停一秒以上，停在谁的决策上谁就超时，平均耗时也被回收拖慢。`lru_cache` 上限取几千条，缓存值用数字和元组（列表、字典、集合会一直被回收器跟踪）。短测的每决策耗时看不出这一点，因为缓存还没填满，结果里的超时次数才是信号。只为减少超时、不改决策的版本走等价替换：最好版本的开发集有超时时，新代码会自己重打开发集，少掉的超时直接体现在分数上。

### 用 C 写热路径

`rule/` 里可以放 `native.c`（以及它 include 的同目录 `.h`），和 `strategy.py` 一起冻结（[ADR-0017](../../../../docs/adr/0017-rule-candidates-carry-their-own-c.md)）。策略里写 `native = _fast.load_native(__file__)`，得到它编译出的模块：模块名 `native`，入口 `PyInit_native`，每台机器按源码只编一次，缓存在包外。start 开跑前会在对手池运行时下先编一遍，编不过就不开跑，并给出编译器报错。

- 新想法的估值、枚举、递归这类热路径直接写进 C，Python 只负责组织流程和解析观察。可以先在 scratchpad 里用 Python 把想法写清楚、测一测，但提交的版本就是 C 版，不要先交 Python 版、事后再补提速。
- `#include "_fast.c"` 可以直接调用运行时的全部 C 原语：向听 `shanten_raw`/`shanten_keyed`、进张分析 `race_analyze_values`、面子表、竞速估值 `race_waiting`/`race_reshaped` 等。这时 `PyInit_native` 里要先调用 `fast_keys()`。
- 编译参数是 `-O3 -ffp-contract=off`，浮点按书写顺序舍入：照 Python 的运算顺序写，结果就逐位相同。遍历 Python 的 set、dict 时顺序由你自己保证，可参考 `_fast.c` 里的 `py_set_order`。
- 约束和 Python 代码一样：不开进程和线程、不加载别的代码、不回头调用 Python 解释器执行或导入代码。start 会检查 C 源码。
- 把现有的 Python 模块搬进 C 而不改决策，走下面的等价替换。

### 等价替换

只提速、不改决策的改动（重写实现、剪枝、缓存、删掉无用代码）加 `--equivalent` 开跑：

```bash
python -m harness.line start rule "<改了什么>" --why "<为什么更快>" --design-start <时刻> --equivalent
```

harness 不跑开发集，而是在几千局新牌局里让新代码和最好版本面对同一批局面，逐个决策比较，一两分钟出结果。全部一致就直接成为最好版本：它的开发集没有超时就沿用它的成绩，有超时就由新代码重打开发集；有一个决策不同就记为「不等价」，汇报列出前几个不同的局面，完整的 `Observation` 和双方动作存在汇报给出的 `mismatches.pickle` 里，可以对两份代码直接调用 `act` 复现。

决策要逐位一致：浮点运算换了顺序、同分时换了取法，都可能让接近同分的选择翻转，重写时保持原来的运算顺序与平分规则。一次等价替换只做提速，不夹带策略改动；它的实现时间按需要，不受公共手册「10 分钟」的限制。

## 自由对战上场版本

自由对战由常驻脚本 `.local/competition/free_play_strongest.py` 负责，上场版本写在 `.local/competition/entrant.pin`。两条线的每个新的最好版本，都会在汇报里对照当前上场版本（开发集上的配对差）。标出「高于参照线，可以上场」时，wait 在【通知】里说明维护者会直接换上（用户 2026-09-30 授权），你照常循环，不用问用户，也不用自己运行 `promote`。
